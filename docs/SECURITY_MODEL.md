# Security Model

## 1. Purpose

This document defines the local security posture for the Figma MCP bridge. The system runs on the user's machine and can mutate an open Figma document, so it must treat localhost access as sensitive.

## 2. Security Goals

- Only the local user can pair a Figma plugin with the MCP server.
- Only the paired plugin can receive mutation commands.
- Only the paired MCP server session can accept plugin responses.
- Remote hosts cannot control the bridge.
- Malicious web pages cannot pair with or drive the bridge through DNS rebinding or permissive CORS.
- Destructive operations are auditable and bounded.
- Logs are useful without exposing document contents unnecessarily.

## 3. Non-Goals

- This system does not protect against malware already running as the local user.
- This system does not bypass Figma permissions, seats, or plan limits.
- This system does not provide multi-user remote collaboration.
- This system does not run as a hosted cloud service.

## 4. Trust Boundaries

```text
Codex agent process
  -> trusted local MCP process
    -> trusted local WebSocket endpoint
      -> paired Figma plugin UI iframe
        -> Figma plugin main thread
          -> open Figma file
```

Untrusted or semi-trusted inputs:

- Any inbound WebSocket connection before pairing.
- Any browser origin.
- Any command text generated by an agent before schema validation.
- Any node IDs or property names supplied by the agent.

Trusted after validation:

- MCP tool schemas.
- protocol message schemas.
- plugin command schemas.
- paired plugin session.

## 5. Network Binding Policy

Default:

- Bind WebSocket bridge to `127.0.0.1`.

Allowed hostnames:

- `127.0.0.1`
- `localhost`

Disallowed by default:

- `0.0.0.0`
- LAN IP addresses.
- public IP addresses.

Advanced mode may allow non-loopback binding only with an explicit command-line flag such as `--unsafe-host=0.0.0.0`. This mode must print a visible warning and should not be used in normal setup instructions.

## 6. Origin Policy

For WebSocket upgrade requests:

- Read the `Origin` header when present.
- Accept known Figma origins and local development origins.
- Reject unknown browser origins.
- Reject requests with malformed origin values.

Expected allowed origins:

- Figma desktop/plugin origin values observed during local testing.
- `null` or absent origin only if the Figma desktop runtime requires it and the request also passes pairing.

Pairing token validation is still required even when origin is accepted.

## 7. Pairing Token

The MCP server generates a random pairing token on startup.

Requirements:

- At least 128 bits of entropy for machine-readable tokens, or a short human token backed by a session secret.
- Expires after 10 minutes if unused.
- Rotates after successful pairing.
- Never sent to unpaired clients.
- Never written to persistent config.

Pairing flow:

1. User starts MCP server.
2. Server displays pairing token locally.
3. User opens Figma plugin.
4. Plugin asks user for pairing token.
5. Plugin sends `plugin.hello` with token.
6. Server accepts or rejects pairing.

## 8. Session Binding

After pairing:

- Session is bound to one plugin WebSocket.
- Commands route only to that plugin.
- Responses are accepted only from that plugin.
- A second plugin connection is rejected unless the user resets the session.

On disconnect:

- Pending commands fail with `PLUGIN_DISCONNECTED`.
- Session remains resumable for a short grace period if reconnect uses a fresh pairing token.
- Automatic reconnection must not skip pairing unless the server has issued a short-lived reconnect token.

## 9. Command Validation

All commands pass through:

- MCP tool schema validation.
- protocol envelope validation.
- command DSL validation inside the plugin.

Validation rejects:

- unknown command types.
- unsupported node types.
- unsupported properties.
- payloads over size limits.
- batch operations over count limits.
- destructive operations with malformed targets.
- raw JavaScript or function strings.

## 10. Destructive Operations

Destructive operations:

- `deleteNode`
- `batch` containing delete operations.
- bulk text replacement.
- future page-level operations.

Controls:

- Log command ID, operation type, target node ID, and result.
- Return a deletion summary containing deleted node identity.
- Support dry-run for batches.
- Limit batch operation count.
- Stop on first error by default.

## 11. Logging Policy

Log:

- server start and stop.
- port and bind host.
- pairing success or failure without printing rejected tokens.
- command ID.
- command type.
- target node IDs.
- duration.
- error code.

Do not log by default:

- full document trees.
- full text contents.
- base64 image export data.
- pairing token after initial display.
- raw WebSocket payloads containing design content.

Verbose logging may be enabled by an explicit `--debug` flag.

## 12. Windows And WSL

Preferred Windows setup:

- Run Node server directly on Windows.
- Run Figma desktop on Windows.
- Use `localhost` or `127.0.0.1`.

WSL setup:

- Treat WSL as advanced.
- Avoid `0.0.0.0` unless the user explicitly opts into unsafe mode.
- Prefer a Windows-hosted Node process for the WebSocket bridge if Figma runs on Windows.

The documentation should not present unsafe binding as the default solution.

## 13. Dependency And Supply Chain

Controls:

- Pin package versions for MVP.
- Commit lockfile.
- Prefer minimal dependencies.
- Keep Figma plugin code bundled from source.
- Preserve MIT license attribution if reference code is copied or substantially adapted.

## 14. Security Acceptance Criteria

- Server refuses non-loopback connections in default mode.
- Unpaired WebSocket clients cannot send commands.
- Incorrect pairing token is rejected.
- Second plugin cannot take over an active session.
- Unknown command type is rejected before reaching Figma Plugin API.
- Unknown update property is rejected.
- Delete operations are logged with node identity.
- Falsy successful results resolve correctly and do not time out.
